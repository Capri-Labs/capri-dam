[[section-design-decisions]]
== Design Decisions

This section documents the major architectural choices made to achieve a
high-performance DAM on a minimal budget.

=== ADR 1: Use of Fastly IO vs. Self-Hosted Image Processing
**Status:** Accepted

**Background:**
Traditionally, dynamic imaging requires a dedicated server cluster running software like Thumbor or ImageMagick. While the software is free, the infrastructure cost and maintenance overhead (scaling, patching, global caching) are significant.

**Assumptions:**

* Image transformation is a CPU-intensive task.
* Global latency is a high priority for end-user experience.
* We want to minimize "DevOps" time for a small team.

**Requirements:**

* Real-time resizing and format conversion.
* Built-in CDN for global delivery.
* Scalability to handle traffic spikes without manual intervention.

**Decision:**
We will use **Fastly Image Optimizer (IO)** as the primary transformation engine.

**Consequences:**

* **Pros:** Zero server maintenance; pay-as-you-go pricing; world-class performance.
* **Cons:** Monthly usage fees based on requests; dependence on a single vendor for the transformation layer.

=== ADR 2: Metadata-Driven Delivery vs. Pre-rendered Renditions
**Status:** Accepted

**Background:**
Legacy systems often pre-calculate 10-20 sizes of an image upon upload and store them in the cloud. This leads to "storage bloat."

**Assumptions:**

* Storage costs increase linearly with the number of files.
* Frontend requirements change over time (new devices/aspect ratios).

**Requirements:**

* Support for any arbitrary image dimension on-the-fly.
* Minimal storage footprint in S3/Azure.

**Decision:**
We will store only the **Master Asset** and a set of **Metadata Instructions** (focal points, default crops). The URL Generator will construct the required transformation parameters in real-time.

**Consequences:**

* **Pros:** Storage costs reduced by ~90%; total flexibility for frontend developers.
* **Cons:** Requires a robust URL-signing strategy to prevent "denial-of-wallet" attacks via infinite resizing requests.

=== ADR 3: PostgreSQL-Native Search (Lexical + pgvector) vs. a Dedicated Search Service
**Status:** Accepted (supersedes an earlier plan to use a sidecar search
service such as Typesense/Elasticsearch — no such service was ultimately
adopted or shipped)

**Background:**
Relational databases (PostgreSQL) can perform text searches, but a naive `LIKE`/`ILIKE`
approach doesn't scale well to "search-as-you-type" UX or to similarity-based discovery
("find images that look like this one"). Many DAM products solve this by running a
dedicated sidecar search/index service (e.g. Elasticsearch, Typesense, Algolia)
alongside the primary database.

**Assumptions:**

* Users expect fast faceted/filtered search over structured + JSONB metadata.
* A meaningful subset of "search" requests are actually *similarity* requests
  ("more like this"), not keyword matches — these need vector/embedding search,
  which a keyword-only sidecar index wouldn't solve either.
* The team wants to avoid operating and keeping in sync a second stateful service
  (index rebuilds, replication lag, dual writes) for a catalog size that PostgreSQL
  itself can comfortably index.

**Requirements:**

* Fast faceted/filtered search results over metadata (content type, custom schema
  fields, dates, dimensions).
* Support for semantic/visual similarity search ("find similar assets"), not just
  exact/substring keyword matches.
* No dual-write consistency problem between a primary DB and a secondary index.

**Decision:**
Run all search **directly against PostgreSQL** — no external search service was
introduced. Lexical/faceted search (`Api::V1::SearchController`) uses `ILIKE` plus
JSONB `properties` filters and auto-discovered schema-driven facets. Semantic/visual
similarity search uses the **pgvector** extension (`neighbor` gem): each asset gets an
embedding row (`AssetEmbedding`), and the `Asset.nearest_to_vector` scope runs a
cosine-distance nearest-neighbour query (`AssetEmbedding.nearest_neighbors(:embedding,
vector, distance: "cosine")`) directly in SQL.

**Consequences:**

* **Pros:** Single source of truth — no second service to operate, monitor, or keep in
  sync; embeddings and lexical metadata are queried transactionally consistent with the
  rest of the asset record; one fewer moving part in deployment (see
  <<section-deployment-view>>).
* **Cons:** Lexical search is `ILIKE`-based, not a true inverted-index/BM25 engine.
  As of migration `20260716113000_add_trigram_search_indexes_for_lexical_search`,
  the `ILIKE` queries **are** index-backed via `pg_trgm` GIN indexes (on
  `assets.title`, `properties->>'original_filename'`, `properties::text`,
  `properties->>'content_type'`, and `folders.name`) — this closes the
  "sequential scan on every request" risk without changing substring-match
  semantics. A `tsvector`/full-text engine (or a real sidecar) remains a
  future option if ranked relevance scoring is ever required. See
  <<section-technical-risks>>.

=== ADR 4: Closure Table for Group Hierarchy vs. Adjacency List
**Status:** Accepted

**Background:**
User groups must support multi-level nesting (e.g. `everyone → Marketing → EMEA → Hamburg`)
so that folder permissions cascade through the hierarchy. A simple parent_id adjacency list
requires recursive SQL to traverse ancestors, which is expensive and varies across databases.

**Assumptions:**

* Group hierarchies will rarely be deeper than 4–5 levels.
* Permission evaluation happens on every authenticated request.
* We must avoid N+1 queries when resolving all ancestors of a user's groups.

**Requirements:**

* O(1) lookup: "Is group B an ancestor of group A?"
* Efficient query: "Give me all descendants of group X."
* Standard SQL (no PostgreSQL-specific `WITH RECURSIVE` required in hot paths).

**Decision:**
We use the **Closure Table** pattern (`user_group_closures`), storing every
ancestor-descendant pair with a `distance` column alongside the standard `parent_id`
foreign key on `user_groups`. The `parent_id` column is kept in sync by `add_child`
to support ActiveRecord associations; the closure table is the authoritative source for
hierarchical queries in controllers and the RBAC engine.

**Consequences:**

* **Pros:** All ancestry/descendancy queries are simple `WHERE ancestor_id = ?` or
  `WHERE descendant_id = ?` lookups; no recursive SQL needed in hot paths.
* **Cons:** Writes are more expensive (must insert multiple closure rows on `add_child`);
  `parent_id` FK must be explicitly maintained in sync with the closure table.

=== ADR 5: Hybrid Monolith (Rails + React) vs. Separate SPA
**Status:** Accepted

**Background:**
Many modern projects split into a separate SPA repository (React) and a separate API
repository (Rails). While this provides strong decoupling, it adds significant
operational complexity: two repos, two CI pipelines, CORS configuration, and a more
complex local development environment.

**Assumptions:**

* The admin portal is exclusively used by authenticated admin users — not the public.
* The team is small; reducing repository fragmentation saves engineering time.
* Server-side rendering is not required for the admin UI.

**Requirements:**

* Single codebase for ease of maintenance and atomic commits.
* React components with full interactivity where needed.
* Standard Rails routing and authentication (Devise + Turbo).

**Decision:**
Use the **Hybrid Monolith** pattern. Rails serves HTML views that contain React
mount points (`<div data-react-component="...">` attributes). The `application.js`
entry point selects and renders the correct component. This provides the interactivity
of an SPA within the stability and simplicity of a Rails application.

**Consequences:**

* **Pros:** Single repo; single CI pipeline; Devise auth works natively; atomic
  commits across backend + frontend changes.
* **Cons:** React components cannot be deployed independently; frontend bundle is
  part of the Rails asset pipeline; less flexibility if a public-facing SPA is needed later.

=== ADR 6: App-Observed Asset Usage Stats vs. CDN Edge Analytics
**Status:** Accepted

**Background:**
The AssetViewer displays view/download/share counters for each asset. In production, the
actual file bytes are frequently served directly from the CDN or a signed S3/GCS/Azure URL
(see `AssetUrlHelper#asset_url_for`), so Rails never observes the byte-serving request
itself. A naive "count every request that hits the Rails controller" approach would
therefore under-count (or simply not know about) the majority of real downloads.

**Assumptions:**

* Exact edge-level bandwidth/hit totals (including hot-linked traffic that never touches
  the app) are a "nice to have", not a hard requirement for the first iteration.
* Knowing when a user *opened*, *downloaded*, or *shared* an asset from within the app is
  valuable on its own and must be accurate and real-time.
* CDN providers (Akamai, Fastly, Cloudflare — see `app/services/cdn_adapters/`) each expose
  their own analytics/reporting APIs, but integrating them requires async polling/webhooks,
  not a synchronous request-response cycle.

**Requirements:**

* Statistics must reflect real, attributable user actions — never fabricated placeholder
  numbers.
* The feature must work identically regardless of which storage/CDN backend is active.
* The data model must not corrupt or misuse existing tables (see the `audit_logs.auditable_id`
  integer-vs-UUID caveat below).

**Decision:**
Record usage as explicit, app-observed events via `POST /api/v1/assets/:id/track_event`
(`view` | `download` | `share`), called by the frontend at the moment the user *initiates*
the action — opening the AssetViewer, clicking Download, or copying the share link — rather
than when the CDN actually streams the bytes. The one exception is the watermarked-proxy
download (`GET /api/v1/assets/:id/watermarked`), which streams bytes through Rails itself, so
that action logs a confirmed download server-side.

Events are stored in a **dedicated `asset_usage_events` table** (`AssetUsageEvent` model,
UUID `asset_id` foreign key) rather than reusing the existing `AuditLog` model: `audit_logs.auditable_id`
is an `integer` column originally sized for `User`'s bigint ids, and would silently
truncate/corrupt a UUID `Asset` id if reused polymorphically. `Asset#usage_stats` aggregates
these events into `{ views:, downloads:, shares: }`, exposed via `GET /api/v1/assets/:id/stats`
and the GraphQL `Asset.usageStats` field, and surfaced in the AssetViewer toolbar (a popover,
not a tab, so it's visible without switching tabs).

**Consequences:**

* **Pros:** Real-time, user-attributed counts with no external dependency; works the same
  in every environment (local, CDN-backed staging, production); safe UUID-typed storage.
* **Cons:** Does not capture anonymous/hot-linked traffic that never touches the app (e.g. an
  externally shared CDN URL opened directly in a browser); "download" for the original file
  is counted at *intent* time, not at guaranteed byte-completion time, since the actual
  transfer usually happens between the browser and the CDN/S3, outside Rails' visibility.
* **Follow-up:** For edge-level bandwidth/hit totals, reconcile nightly via each CDN adapter's
  reporting API (Cloudflare GraphQL Analytics, Fastly Real-Time Analytics, Akamai Reporting) and
  merge into `Asset#usage_stats` as a secondary, clearly-labelled data source.


=== ADR 7: Named UI Extension Slots vs. a Runtime Plugin Hook Bus
**Status:** Accepted

**Background:**
Roadmap rows 37 and 69 ask for a documented way to add custom panels, dashboard
widgets and Properties tabs "without forking the React source". Custom
_metadata fields_ are already fully supported through Metadata Schemas; this ADR
is about extending the _UI itself_.

Three facts about the current codebase set the constraints, and each was
verified rather than assumed:

* There is **no existing registry to generalise**. `Admin/widgets/BarChartWidget.jsx`
  is 29 lines and is referenced only by its own Jest test — it is not mounted
  anywhere in the product. This is greenfield, not a refactor.
* The frontend is a **build-time static import map**. `components/Registry.jsx`
  maps a `data-view` key to a component, `application.js` looks the key up and
  mounts the island. Every component is compiled into one esbuild bundle. There
  is no runtime module loading anywhere in the app.
* **The page has no security boundary inside it.** Authentication is a Devise
  session cookie, and the CSRF token is published in a `meta` tag that any
  script in the document can read (`utils/adminUtils.js`, `utils/format.js`).
  `config/initializers/content_security_policy.rb` is commented out in its
  entirety, so no CSP is enforced.

Taken together: any JavaScript that reaches the main bundle can read the CSRF
token and issue authenticated same-origin requests as the current user,
including administrative ones. "Loading a third-party widget" and "granting a
third party the estate" are, today, the same act.

**Assumptions:**

* The near-term demand is first-party and customer-specific composition — a
  customer wants _their_ panel in _their_ deployment — not an open marketplace
  of untrusted plugins.
* Extension authors are frontend developers who can build and deploy an
  artefact; they are not writing code in a browser text box.
* An extension API that breaks on every release is worse than no extension API,
  because it converts one fork into a permanent maintenance relationship.
* A slot that renders nothing is an acceptable failure; a slot that takes down
  the asset viewer is not.

**Requirements:**

* Enumerable, documentable extension points — we must be able to say exactly
  what the API _is_.
* A stated security boundary, not an implied one.
* A versioning and deprecation story defined before the first extension exists.
* Failure isolation: a faulty extension must degrade locally.

**Decision:**

*1. Extension points are named slots, not a hook bus.*
A slot is a declared location with a declared prop contract; the host renders
whatever is registered for it. We explicitly reject a publish/subscribe hook bus.
A bus is open-ended — every hook becomes a compatibility commitment the moment
someone depends on it, and the semantics that matter most (ordering between
subscribers, whether a subscriber may mutate what it is handed, what happens
when two extensions disagree) are precisely the ones a bus leaves unspecified.
Slots are finite and enumerable, so they can be listed, documented, versioned
and tested, and the blast radius of an extension is bounded by where it renders.

*2. The security boundary: trusted-first-party now, sandboxed-untrusted later —
and never third-party JavaScript in the main bundle.*
This is the crux of the ADR, so it is stated as two tiers with an explicit
prohibition between them.

**Tier 1 (ships in Phases 17–18).** Extensions are **first-party and trusted**:
source-level, code-reviewed, compiled into the bundle exactly like every other
component. This is honest about what it is — _composition from configuration_,
not a plugin sandbox — and it is worth having on its own, because it replaces
hardcoded JSX with a registry and a persisted layout. It removes the fork for
people who control their own build. It does **not** make it safe to run someone
else's code, and the documentation must not imply that it does.

**Tier 2 (specified here, deliberately not built yet).** Untrusted third-party
extensions run in an **iframe with `sandbox="allow-scripts"` and without
`allow-same-origin`**, served from a **separate origin**. Omitting
`allow-same-origin` is the whole point: the frame gets an opaque origin, so it
cannot read the session cookie, the CSRF token, or the host DOM. It talks to the
host only over `postMessage` using a versioned, schema-checked message contract,
and it reaches the API with **its own Doorkeeper token** carrying narrowed
scopes (`read`/`write`/`admin` already exist), never the user's session. A
third-party extension therefore has _less_ authority than the user who installed
it, which is the property that makes it installable at all.

**Prohibited, permanently:** loading untrusted third-party JavaScript into the
main document, by any mechanism — bundled, `import()`-ed, or injected via a
script tag. There is no configuration of that arrangement which is safe, because
the CSRF token is readable from the DOM by design.

**Prerequisite for Tier 2:** a Content-Security-Policy must be enabled first. It
is currently commented out, and shipping a sandbox while the page itself permits
arbitrary script sources would be a boundary in name only.

*3. Versioning.*
The slot name plus its prop contract _is_ the public API. Adding a slot, or
adding a prop to an existing one, is a minor change. Renaming or removing a slot,
or changing the meaning of an existing prop, is a major change. Every extension
declares the major `apiVersion` it targets; the host refuses to render an
extension whose declared major it does not implement, rendering a visible
placeholder rather than throwing — a silently absent panel is indistinguishable
from a bug in the extension. A slot may only be removed after one minor release
in which it is deprecated and logs a console warning. Every slot render is
wrapped in an error boundary, so a thrown extension degrades to "this panel
failed to load" and the surrounding screen survives.

*4. Which slots ship first.*
`dashboard.widget` in Phase 17 (widget key → component plus a declared data
contract, with per-user layout persisted), then `asset.inspector.tab` and
`asset.properties.section` in Phase 18. These three are chosen because they are
read-mostly presentation surfaces. Upload and ingestion, authentication, and
settings are deliberately **not** extensible in the first iteration: they carry
the highest blast radius and the least well-understood contracts.

**Consequences:**

* **Pros:** The API surface is finite and can be documented in full. Tier 1 is
  achievable with no new security machinery, because it grants no new authority
  to anyone. The security posture is written down before an extension exists,
  which is the only time it can be chosen freely. Error boundaries and the
  `apiVersion` refusal make third-party breakage local and legible.
* **Cons:** Tier 1 does not satisfy "without forking" for a customer who does
  not control their own build — they must still build and deploy an artefact.
  This is a real and acknowledged limitation, and the honest answer is that
  closing it fully requires Tier 2. Named slots also mean every new extension
  point is a deliberate act; there is no generic escape hatch, so demand for a
  slot we did not anticipate becomes a change request rather than something an
  extension author can work around.
* **Risk:** the value of a slot is only proven by a real consumer. Phase 18 must
  therefore ship a reference extension alongside the API, because an extension
  API with no worked example is indistinguishable from an untested one.
* **Follow-up:** enable CSP (prerequisite for Tier 2); revisit Tier 2 only when
  there is a concrete untrusted-extension requirement, since building a sandbox
  for a hypothetical consumer is the most likely way for this feature to be
  over-built.
