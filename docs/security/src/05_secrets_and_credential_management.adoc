== Secrets & Credential Management

=== Rails encrypted credentials

Application-wide secrets (third-party API keys, default admin bootstrap
values, mailer credentials, etc. that aren't per-record data) are stored in
`config/credentials.yml.enc`, encrypted with a master key
(`config/master.key`, **never committed** — it's git-ignored by the Rails
default `.gitignore`). Both the README and `CONTRIBUTING.md` state this
explicitly:

[quote]
Credentials are encrypted in `config/credentials.yml.enc`. Supply the
`RAILS_MASTER_KEY` (or `config/master.key`) before running setup.

In deployment, the master key (or an equivalent `RAILS_MASTER_KEY`
environment variable) must be supplied out-of-band by the deployment
pipeline — Kamal secrets, a cloud secrets manager (AWS Secrets
Manager/Parameter Store, Azure Key Vault), or a CI secret store — never
committed to source control. See the per-target deployment guides
(link:../deployment-guide-kamal/[Kamal], link:../deployment-guide-aws/[AWS],
link:../deployment-guide-azure-kubernetes/[Azure/Kubernetes]) for exactly
how each environment injects this key.

=== Per-record encrypted secrets vs. application-wide secrets

It's important to distinguish two different secret stores in this codebase:

[cols="1,2,2", options="header"]
|===
| Store | Scope | Examples

| `config/credentials.yml.enc`
| Application-wide, one value shared by the whole deployment.
| Mailer SMTP credentials, third-party platform API keys not tied to a
  single tenant/connector.

| `ActiveRecord::Encryption` columns
| Per-record, tenant/connector/configuration-specific.
| `SystemConnector#auth_token`, `CdnConfiguration#settings`,
  `EmailDelivery#payload`, `Setting#value` (see
  <<section-data-protection-and-encryption,Data Protection &
  Encryption>>).
|===

A new integration that needs a secret scoped to a specific connector,
tenant, or configuration record should use an encrypted column on that
record — **not** a new key added to `credentials.yml.enc`, which is
appropriate only for genuinely global, deployment-wide secrets.

=== Webhook secrets

Each `SystemConnector` has its own `webhook_secret`, used to verify inbound
webhook signatures (see
<<section-network-and-application-security,Network & Application
Security>>). This is intentionally per-connector rather than a single
shared application secret, so that revoking or rotating one connector's
webhook secret (e.g. after a suspected leak) does not require rotating
every other connector's trust relationship.

=== CI/CD secrets

GitHub Actions secrets (`SEMGREP_APP_TOKEN`, deployment credentials used by
the deploy workflows, `GITHUB_TOKEN` for auto-assign/labelling automation)
are stored in the repository's encrypted GitHub Actions secrets store, never
in workflow YAML or committed files. `.github/workflows/sast.yml` is a
representative example of consuming a secret this way
(`env: SEMGREP_APP_TOKEN: ${{ secrets.SEMGREP_APP_TOKEN }}`).

=== Secret leakage prevention

TruffleHog OSS scans every push/PR diff (and the full repository history on
the weekly scheduled run) for verified, live secrets —
`.github/workflows/sast.yml`'s `secrets-scan` job. Because it uses
`--only-verified`, it specifically avoids false-positive noise from
test-fixture-looking strings, focusing instead on secrets that are
confirmed to be live/valid against the originating provider's API. This is
a detective control (catches a secret that has already been committed) and
should not be relied upon as the only safeguard — the primary control
remains never committing secrets in the first place, per this repository's
`AGENTS.md`/`CLAUDE.md` hard rules.

=== Rotation guidance

[cols="1,2", options="header"]
|===
| Secret type | Rotation trigger / cadence

| `RAILS_MASTER_KEY` / `config/master.key`
| On suspected compromise only (rotating requires re-encrypting
  `credentials.yml.enc` and redeploying with the new key everywhere) —
  there is no automatic rotation schedule today; tracked as a roadmap item.

| `SystemConnector#webhook_secret`
| On suspected compromise, or when off-boarding a third-party integration
  partner.

| Personal Access Tokens
| User-initiated; a PAT can be deactivated (`active: false`) at any time
  without deleting its audit history. There is no automatic PAT expiry
  today — tracked as a roadmap item (see
  <<section-security-roadmap,Compliance Mapping & Security Roadmap>>).

| Doorkeeper OAuth2 access/refresh tokens
| Governed by the TTL configured per-application in
  `config/initializers/doorkeeper.rb`; review this file directly for the
  active configuration in a given deployment, since several stricter
  defaults ship commented out.
|===
