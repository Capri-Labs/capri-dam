| ✅ Done | AVIF delivery | Delivery requests are answered in AVIF (preferred) or WebP when three parties agree, each of which can veto. The *administrator* must have enabled the format in `image_optimizer_formats` on the active CDN configuration — the allow-list that already existed now governs what the application itself produces as well as what an edge CDN may serve, so one switch means one behaviour with or without a CDN in front, and with no active configuration nothing is transcoded at all. The *client* must name `image/avif` or `image/webp` explicitly in `Accept`: a wildcard is not evidence, because every browser sends one regardless of what it can decode, and a browser handed a format it cannot decode shows a broken image rather than a larger one — Safari and older Chrome/Firefox advertise WebP but not AVIF, which is why the negotiator falls back rather than assuming. The *encoder* must come out smaller: AVIF's fixed overhead can exceed what it saves on small images, and serving a larger file would be a pessimisation disguised as a modernisation, so a derivative that fails to pay for itself is discarded and the original served. Only JPEG and PNG are re-encoded — SVG because re-encoding a vector destroys the reason it is one, GIF because it may be animated and a single-frame AVIF would silently truncate it. Derivatives are content-addressed files keyed on the source's size and mtime plus the encode settings, not `renditions` rows: a delivery derivative is disposable and giving it a database row would mean inventing a storage backend for it and keeping row and file in step on every re-upload, whereas the digest gets invalidation for free. `Vary: Accept` is set on every response including 304s and untranscoded originals, since a shared cache keyed only on the URL would hand an AVIF to a client that cannot decode it; the ETag is computed over the bytes actually sent, since a shared one would let a client holding the JPEG revalidate into a 304 and never receive the AVIF. Every failure path serves the original rather than raising — this runs inline on an image request, so a missing codec must degrade, not 500. Request-time *resizing and cropping* remain edge-only; the in-application pipeline negotiates format.
| ✅ Done | Kamal 2 deployment | Production deployment via Kamal 2 (`kamal` 2.12.0). `config/deploy.yml` defines web + Sidekiq worker roles, `kamal-proxy` with automatic Let's Encrypt TLS and a `/up` health check, GHCR image pull matching `.github/workflows/docker.yml`, and PostgreSQL (pgvector) + Redis accessories with persistent volumes. `.kamal/hooks/pre-deploy` gates on a clean tree and green CI; `.kamal/hooks/post-deploy` runs an HTTPS smoke test; `.kamal/secrets` references env vars only. The 10-chapter playbook in `docs/deployment-guide-kamal/` (prerequisites → configuration → secrets → accessories → first deploy → routine deploys/rollback → SSL → monitoring → backup/DR) is published as HTML + PDF by `.github/workflows/main.yml`.
| 📋 Planned | Multi-site isolation | Tenant-scoped storage and RBAC for agency use cases.
| 📋 Planned | DAM-to-DAM federation | Cross-instance asset sharing via signed GraphQL federation.
| ✅ Done | AI auto-tagging | A vision model proposes tags; only a person applies them. `AiTagSuggestion#accept!` is the single code path in the application that writes a machine-derived label into `assets.properties["tags"]` — a gateway callback, however well-authenticated, can create nothing but `pending` rows. That separation is the point: tags drive search, collection filters and rights rules, and a vocabulary that silently blends curated terms with speculative ones cannot be separated again cheaply. Runs and suggestions are distinct tables because their lifecycles differ — the run row makes dispatch idempotent (the worker no-ops unless the run is still `queued`), gives the callback something to correlate against, and makes a gateway outage *visible* rather than indistinguishable from a model that found nothing to say, while each suggestion carries its own accept/dismiss state, decider and timestamp. `Ai::TagSuggestionImporter` is the trust boundary and discards three classes of candidate: below the 0.55 confidence floor, already present on the asset (compared after normalisation, so `Sunset` matches `sunset`), or previously dismissed. Dismissed rows are *kept, never deleted*, and are consulted across every later run for that asset — deleting a rejection would let the same label be re-proposed forever. A 25-suggestion cap bounds the triage burden however chatty the model is. Confidence is nullable and meaningful (a model that reports none is not one reporting zero) and out-of-range values are clamped rather than rejected, since a gateway reporting `1.4` has a scaling bug but probably a real label; a `CHECK` constraint guarantees the column. `profile` is an allow-listed key, never a prompt — a caller able to dictate the instruction could redirect the model under our credentials — and unrecognised values fall back to `general_subject` instead of passing through. The upload trigger is off by default (`ai_auto_tagging_enabled`), images only, and rescued, because the asset is already stored and `ready` by then and a tagging failure must never fail the upload; such runs have a nil `requested_by`, since nobody asked. Conflicting requests, replayed callbacks and double-decisions all return `409`. Triage lives in the AI tab of the asset viewer (`AiTagSuggestionsPanel`).
| ✅ Done | Bulk copy (folders & assets) | "Copy to…" action mirroring the existing "Move to…" action — select any mix of folders/assets and copy them into a new destination in one request (`POST /api/v1/copy_operations`). Recursively duplicates folders, shares the source's ActiveStorage blob instead of re-uploading bytes, and auto-resolves name collisions.
| ✅ Done | Bulk/folder ZIP download | "Download" action on a folder or any multi-asset selection streams a ZIP built asynchronously by `AssetDownloadWorker`, with a live progress bar, queue-awareness (a second download while one is running is queued, not run concurrently), and the finished ZIP link delivered to the user's Inbox and notification bell.
| ✅ Done | Manual static renditions | Add and delete alternative stored forms of an asset — a print-ready CMYK TIFF, a hand-cropped social variant, a broadcast proxy — from a Renditions tab in the asset inspector and from `/api/v1/assets/{id}/renditions`. A rendition is deliberately *not* a version: a version answers "what did this look like at time T" and the newest supersedes the rest, whereas every rendition is current at once, so filing a CMYK master as a version would make the web original read as superseded history. `kind` is a match key rather than a label — lowercase underscored, unique per asset, so a second upload of an existing kind is a `422` rather than a silent replace — with an open vocabulary (`print_cmyk`, `social_square`) because which forms matter is an organisational question, but `thumbnail`/`web_preview`/`poster` reserved to the pipeline so other code may keep assuming a thumbnail came from the thumbnailer. The `NOT NULL` `storage_backend_id` is resolved once at upload and the bytes written through *that same record's own adapter*, never the currently-active one: resolving at read time would silently break every rendition uploaded before a provider switch, since bytes do not move because a setting did. With no active backend the upload is refused with `503` rather than stored somewhere unnameable. The object is written before the row is validated and deleted again if validation fails — an orphaned object cannot corrupt a later read, a row pointing at nothing can — and purged on `after_destroy_commit` so a rolled-back transaction cannot orphan the row instead. Dimensions are derived server-side via MiniMagick, never accepted from the caller, and `storage_key` is never serialised.
| ✅ Done | Direct Publish REST action | `POST/POST /api/v1/assets/:id/publish`\|`/unpublish` — publishing an asset no longer requires building a workflow first. "Manage Publish" is a dedicated menu next to (not inside) *Tools* in the Explorer, offering immediate Publish/Unpublish plus "…Later" scheduling (`ScheduledPublishAction` + `PublishSchedulerWorker`, polled every 5 minutes) for a future date/time. Asset-only — never shown for a selection containing folders.
| ✅ Done | Contextual metadata rules (Choices / Requirement / Visibility) | Metadata Schema fields can depend on another `select` field's value, configured entirely via the Schema Editor UI (no code changes): **Choices** narrows a dependent `select`'s options (`field.rules.cascade`); **Requirement** dynamically marks any field type required (`field.rules.requirement`); **Visibility** shows/hides any field type (`field.rules.visibility`). Resolved client-side by `AssetMetadataPanel#resolveFieldRules`, with save-time validation across all tabs.
| ✅ Done | Custom "funny 404" error page | A shared `ApplicationController#render_not_found` (triggered by `ActiveRecord::RecordNotFound` and by a `config/routes.rb` catch-all for unmatched routes) replaces raw Rails diagnostics pages with an illustrated, on-brand 404 screen for browser navigation, and a small structured `{ error: ... }` JSON body for API/fetch clients — e.g. a stale `/api/v1/asset_downloads/:id/download` inbox link no longer surfaces a stack trace.
| ✅ Done | Image coordinate annotations | Draw a pin, rectangle, ellipse, arrow, line or freehand markup directly on an image preview and attach it to a comment. Geometry is stored *normalised* (0..1, upper-left origin, DB `CHECK`-constrained) plus an `svg_path` in a `viewBox="0 0 1 1"` space, following the W3C Web Annotation Data Model's FragmentSelector/SvgSelector split — so one annotation lands correctly on a thumbnail, a full-size preview, a CDN transform and a zoomed viewport alike, and never breaks when a rendition is regenerated. `annotation_targets` also records the source dimensions/rotation at annotation time so the geometry can later be re-projected onto a differently sized version. `AnnotationOverlay.jsx` renders the shapes as individually selectable SVG nodes stacked on the preview; clicking a marker jumps to its thread and vice versa.
| ✅ Done | General asset commenting | A standalone, threaded review conversation on any asset (`comment_threads` / `comments`), open to anyone with `:read` on the folder — deliberately *not* `:modify`, because reviewing is not editing. Replaces the previous situation where the only "comment" in the product was the approve/reject note on a workflow task. **Threads belong to the asset; each comment records the `AssetVersion` it was written against** — so a thread survives re-uploads instead of being orphaned by them (the limitation every comparable product documents). Lifecycle is `open → addressed → verified → resolved`, with `verified` reserved for a reviewer confirming a fix actually landed. `@mentions` reuse the existing `MentionDetectionService`/Inbox/notification-bell/email pipeline; edits stamp `edited_at` and deletes are soft, so the trail cannot be silently rewritten. Editing or deleting a comment is author-only. REST at `/api/v1/assets/:id/comments`, `/api/v1/comment_threads/:id` and `/api/v1/comments/:id`; UI in the Explorer asset viewer's *Comments* tab.
| ✅ Done | Video timestamp & range annotations | Comment on a single frame or on an in/out *range*, with a custom frame-accurate transport (`VideoAnnotationPlayer`): frame stepping, SMPTE timecode readout, a marker track on the scrubber, loop playback over the selected range, and the standard NLE keyboard bindings. Markup drawn on the video is stamped with the frame it was drawn over and only appears while the play head is inside that range, so an arrow pointing at a car does not linger after the car has driven off. A spatially-empty `time` shape lets a reviewer comment on a moment without drawing anything. Frame rate now comes from ffprobe (`avg_frame_rate`, falling back to `r_frame_rate`), keeping the exact rational so 29.97 can be told apart from a true 30 and drop-frame applied correctly.
| ✅ Done | Cross-version comment lineage | Auto-answer "was this feedback actually addressed?" by re-projecting a thread's stored (normalised) bounding box onto a newer version and running the canvas pixel-diff that `AssetVersionsTab.jsx` already implements *inside that region* — surfacing an automatic "changed in v3" / "unchanged since v2" marker on each thread, and offering side-by-side before/after crops of just the annotated region. No reviewed competitor carries comments forward across versions at all, so this is a genuine differentiator rather than parity work.
| ✅ Done | Guest reviewers & external review links | Let a client review and comment on an asset or a whole collection without a Capri account, via a revocable, time-boxed link (`/s/reviews/:token`). Capri already had *read-only* collection share links built on Rails `signed_id`, but a self-describing signed token cannot be revoked, carries no identity and cannot be scoped or metered — all three of which a link granting **write** access needs — so review links are DB-backed (`review_links`, `review_guests`) while share links are left as they are. Only a SHA-256 digest of the token is stored, so the raw token is shown exactly once at creation and a database dump yields no working review URLs; an optional passphrase (bcrypt, human-chosen, so a slow digest is the right one there) adds a second factor shared out of band. Expiry is mandatory and hard-capped at 180 days. A collection link resolves through *live* membership, so removing an asset from the collection withdraws it from every outstanding link at once. Guests are identified for **attribution, not authentication** — a `ReviewGuest` is not a `User`, so it has no credentials to compromise and no permission surface to widen, and a self-asserted email is never matched against an existing account. The guest surface shares serialisation with the internal API but *no authorisation path*: there is no `if guest then skip the permission check` branch anywhere, and the guest serialiser is an allow-list, so internal staff emails and user ids cannot leak. `comment_threads.visibility` (`internal` / `guest`) filters at the query, not in the view. Previews and downloads are proxied through the app rather than handed out as signed storage URLs, so revocation actually revokes. Guests can open threads, annotate and reply; they cannot resolve, verify, reopen, edit or delete. Managed at `/api/v1/review_links`, which requires `:modify` on the target — sharing outside the organisation is a stronger act than discussing internally.
| ✅ Done | Annotation interoperability & export | Emits and ingests W3C Web Annotation JSON-LD, so a proofing vendor, archive or approvals system is a file copy rather than a bespoke integration. Geometry travels as percentage media fragments (never pixels, so an export is not tied to whichever rendition was on screen), with an `SvgSelector` for non-rectangular shapes and a `t=` temporal fragment for video. What the standard cannot carry — shape, stroke style, exact frame rate, drop-frame, thread grouping — rides *alongside* it under a namespaced `capri:` prefix, so third parties see valid W3C while Capri round-trips losslessly. Import treats the file as untrusted input: attribution is never honoured (the uploader is always the author, the file's claim kept as provenance), visibility is forced to `internal`, and a claimed `resolved` is gated on `:modify` so an upload cannot silently close outstanding feedback. Also renders an annotated PDF contact sheet for offline sign-off — markers drawn as vectors over the preview so they stay crisp in print, degrading to a text-only sheet rather than failing if the preview is unreadable — and fires HMAC-signed review webhooks (`comment.created`, `comment.resolved`, `thread.created`, `thread.resolved`, `thread.reopened`) from a proper subscription registry, scoped per asset or folder, distinct from the workflow engine's per-step webhook action.
| ✅ Done | AI review assistant | A vision model runs over an asset and posts what it finds (brand-guideline breaches, unreadable contrast, logo outside the safe area, off-brand colour) as *real* annotated comments — the same threads, normalised geometry and version binding as a human remark — which a person then accepts or dismisses. Findings are stored as ordinary `CommentThread`s rather than in a parallel suggestions table, so region-diff across versions, W3C export and the PDF contact sheet all applied to machine output on day one; a separate table would have needed every one of them reimplemented and the two would have drifted. What separates a suggestion from feedback is `comment_threads.suggestion_state`, NULL for every human thread and `pending` for a machine one: until somebody accepts it a finding is excluded from the thread list, from exports and from the guest surface, and is additionally created `internal` so the guest query excludes it twice over — an unreviewed machine guess reaching a client is the worst outcome this feature has. Accepting records *who decided* but never rewrites the comment's author: `agent_type` stays `software` for ever, because laundering machine output into a person's name would destroy exactly the audit trail that column exists to keep. Dismissed findings are kept, not deleted — a false positive is the only evidence available for tuning the model. Inference stays in the AI gateway (Rails publishes `ai_review.dispatch` over Redis and the gateway calls back with the shared secret), the dispatch carries a callback URL rather than storage credentials so revoking a run revokes its access, and the callback payload is treated as untrusted: coordinates clamped into the unit square, bodies capped, low-confidence findings dropped, runs capped at 50, one malformed finding skipped rather than fatal. Requesting a run needs `:modify`, not the `:read` ordinary commenting needs, since it discloses the asset to an external service and spends budget; `profile` is an allow-list, not a free-text prompt. Triage lives in the Comments tab of the asset viewer, above the human threads, because a suggestion is a comment thread awaiting admission — accepting one makes it appear in the list directly below. Suggestion markers are drawn on the shared annotation overlay in the assistant's purple, stamped server-side so the UI and the W3C export cannot disagree about which marks are machine-made. There is deliberately no "accept all": the assistant's value is that a human looked at each claim, and a bulk button would quietly turn it into an unreviewed bot posting into the client's review. The queue polls only while a run is in flight — findings arrive by gateway callback, nothing pushes to the browser — and stops the moment the run is terminal.
| 📋 Planned | UI extension/plugin framework | A documented hook/widget API so third parties can add custom panels, dashboard widgets, or Properties-page tabs without forking the React source (custom *metadata fields* are already fully supported via Metadata Schemas — this item is about extending the *UI itself*, e.g. new widget types beyond the single built-in `BarChartWidget`). The contract is now settled in *ADR 7* (`docs/architecture/src/09_design_decisions.adoc`): named slots rather than a hook bus, first-party trusted extensions compiled into the bundle first, and untrusted third parties confined to a cross-origin `sandbox="allow-scripts"` iframe with their own narrowed Doorkeeper token — never third-party JavaScript in the main document, since the CSRF token is readable from the DOM by design. Implementation follows in the widget registry and the inspector/properties slots.
| ✅ Done | Distribution portal for external stakeholders | *Phase 12 is complete.* Sharing a collection externally previously meant a signed, time-expiring link: whole-collection, all-or-nothing, unbranded, and with no record of what was actually taken — and, as this phase found, it listed every asset's title and thumbnail with no rights filter at all, while a share-token holder could fetch the *bytes* of an `internal_only` asset through `/api/v1/assets/local/:uuid`. Both leaks are fixed. A portal is now a `ReviewLink` with `kind: "portal"` rather than a parallel model, because the security-critical apparatus — digest-only bearer token, bcrypt passphrase, revocation, hard expiry ceiling, link-scoped guest identity and the Phase 10b rights filter — already exists and is specified; a second copy is how the next security fix lands in only one of them. Kinds never mix: a portal token is refused by the review surface and vice versa, in both the guest controllers and the management API. Three *independent* gates decide what a recipient sees — live collection membership, an explicit `PortalGrant`, and `Rights::DownloadPolicy` — so revoking any one withdraws the asset. Absence of a grant is the denial, because an implied grant means a portal handed out last month silently starts offering this month's work. A grant records only that the sender is *willing*; it cannot widen rights, so `download` on an internal-only asset is recorded but never honoured — and the API reports `distributable_count` against `granted_count` so the gap is found while configuring rather than from the partner's email. Refusals are graded: view-only returns 403 (the recipient can already see the file, so denying its existence reads as a bug), while ungranted or rights-restricted returns 404 (it must be indistinguishable from something never shared). `download_url` is null rather than a URL that would 403, so no unusable button is ever rendered. Grants are declarative — the set you send replaces the set that exists — because an incremental "add these" API makes removal something you must remember separately, and the permission you forget to remove is the one that leaks; they are also confined to the link's own target, and an unrecognised permission falls back to `view`. Branding is whitelisted rather than escaped (it reaches an `img` source and inline CSS, where a `url()` payload survives HTML escaping intact), and invalid values are dropped rather than rejected. `portal_downloads` records only *successful* deliveries, and its writes swallow their own errors — losing a log line is a reporting gap, but a partner's download failing because a logging insert raised is an outage. Revocation preserves the row, since the download records point at it for provenance. The guest surface is a separate ~3.6 MB esbuild entry point carrying no permission model of its own. This phase also fixed a pre-existing bug that had broken *all* guest review previews and downloads since Phase 6: `StorageManager.read_file_from_adapter` takes two arguments and was called with one, and a bare `rescue StandardError` turned the resulting `ArgumentError` into a silent 404 — only the refusal path had ever been tested, which passes whether or not delivery works. See `docs/developer-guide/src/31_distribution-portal.adoc`.
| ✅ Done | Rights & licensing enforcement | *Phase 10a (data) and 10b (enforcement) are both complete.* The roadmap previously described `usage_terms` and `license_expires_at` as fields "on Asset". They were not columns — they were free text inside the `assets.properties` JSONB blob, and enforcement could not safely be built on them. Usage terms were compared against one exact English literal, so every other spelling (`"internal use only"`, `"Internal-Only"`, `"Confidential"`) failed the comparison and therefore read as *not internal*, i.e. as clearance to expose the asset externally — the bug pointed toward disclosure. Expiry dates were parsed at read time by `Time.zone.parse`, which *raises* on `"2024"` (aborting the compliance scan for a whole collection), returns the year 12 for `"12345"`, and silently rolls `"2026-02-30"` forward to 2 March; the analytics forecast wrapped the equivalent SQL cast in a bare `rescue 0`, so one malformed row anywhere reported "no licences expiring" precisely when the data was worst. *10a* adds typed, constrained columns with a controlled vocabulary (`internal_only`/`editorial_only`/`rights_managed`/`royalty_free`/`public_domain`), an ISO-8601-only expiry parser that rejects locale-ambiguous dates rather than guessing, a backfill that preserves anything unreadable under `*_raw` keys instead of coercing it, and fail-closed normalisation so unrecognised rights text lands on the most restrictive term. Columns and the legacy JSONB keys are kept in step in both directions, so importers and search facets keep working. *10b* routes every byte-delivery path through one `Rights::DownloadPolicy`, because a check written per controller is a check that will be missing from the tenth surface somebody adds. Usage terms and licence expiry block *different* audiences: terms answer "may this leave the organisation" and gate external delivery only; expiry answers "may we use this at all" and blocks export for internal users too. Viewing is deliberately not gated internally — blanking every thumbnail the day a licence lapsed is how a safety control gets switched off — but externally there is no such distinction, since showing a guest an internal-only asset *is* the disclosure. Guest links filter restricted assets out of their *scope* rather than refusing at delivery, so a restricted asset is indistinguishable from one never shared and its title never leaks into a listing; link owners see both `asset_count` and `distributable_asset_count`. Bulk ZIP export filters at the single funnel both hand-picked assets and folder walks pass through, and records every exclusion on `asset_downloads.restricted_items` plus a `RESTRICTED_ASSETS.txt` manifest inside the archive — an archive that silently omits three files is worse than one that refuses, because the recipient assumes it is complete. Download URLs are refused at *issuance*, since a presigned S3/CDN link is served by infrastructure the app never sees. Administrators may export a lapsed asset (someone must be able to archive or replace it), but the bypass never applies externally. The `AssetRightsPanel` management UI reads its vocabulary from `GET /api/v1/rights/usage_terms` so the dropdown cannot drift from what the policy enforces. See `docs/developer-guide/src/30_rights-and-licensing.adoc`.

=== Capability parity checklist (vs. a typical enterprise DAM suite)

The table below was produced by directly auditing this codebase (models,
controllers, GraphQL schema, and React components — not assumptions) against
a checklist of capabilities commonly expected of an enterprise DAM/Assets
product. It is meant to answer "is X implemented, partial, or not built yet"
for planning purposes. Genuine gaps are already reflected as
📋 Planned rows in the <<module-roadmap,product roadmap>> above.

[cols="3,1,5", options="header"]
|===
| Capability | Status | Notes / evidence

| Create folders to organize assets | ✅ Done | Hierarchical `Folder` model (self-referential nesting), full CRUD, breadcrumbs, soft-delete.
| Upload assets | ✅ Done | Single + bulk drag-drop upload, duplicate detection, schema assignment at upload time.
| Publish assets | ✅ Done | `Asset#status` still includes the older workflow-driven `ready`/`approved` states, but publishing is now also a direct, one-click action independent of any workflow: `POST/POST /api/v1/assets/:id/publish`\|`/unpublish` (immediate or scheduled for a future date/time via `ScheduledPublishAction`/`PublishSchedulerWorker`), surfaced through the "Manage Publish" menu next to *Tools*.
| Edit, move, and copy assets | ✅ Done | Edit, move, and copy are all full REST actions (`Api::V1::Assets#update`, `Api::V1::MoveOperations#create`, `Api::V1::CopyOperations#create`). Copy recursively duplicates folders (subfolders + assets), shares the underlying ActiveStorage blob rather than re-uploading file bytes, and auto-resolves destination name collisions.
| Browse, filter, and search assets, including similarity search | ✅ Done | Full-text + faceted REST search, pgvector cosine-similarity semantic/visual search, agentic AI Copilot search mode.
| Add/edit Basic-tab metadata field values (except Smart Tags) | ✅ Done | Schema-driven `AssetMetadataPanel` with per-field `read_only` support; AI-generated tags are shown read-only and separated from manually-editable static tags.
| Add and delete static renditions | ✅ Done | `AssetRenditionsTab` in the asset inspector plus `Api::V1::RenditionsController` (`index`/`create`/`destroy`, nested under the asset so a rendition id cannot reach across to another asset). Create and delete require `modify`, not `read` — adding a rendition changes what the asset *is* to every downstream consumer. Generated renditions are listed and marked but not deletable from the UI: they are reproducible from the source, so deleting one merely invites the pipeline to make it again.
| Download folders, assets, and asset renditions | ✅ Done | Individual asset + individual rendition download; bulk folder/asset ZIP export via `AssetDownloadWorker` with progress polling, queue-awareness, and inbox/notification delivery of the finished link (`Api::V1::AssetDownloadsController`).
| Create asset versions | ✅ Done | Full immutable version history per asset with restore-to-prior-version support.
| Create and perform review tasks on assets | ✅ Done | Workflow approval nodes with configurable assignees/any-all logic, SLA deadlines, and a Workflow Dashboard of pending/active/completed tasks.
| Annotate assets (coordinate/timestamp pins) | ✅ Done | Pin, rectangle, ellipse, arrow, line and freehand markup on image *and video* previews, attached to a comment. Geometry is stored normalised (0..1) with an `svg_path` in a `viewBox="0 0 1 1"` space, per the W3C Web Annotation Data Model, so it survives responsive layout, renditions and CDN transforms. Video positions are stored frame-accurately (`start_frame`/`end_frame`/`fps`/`drop_frame`, with SMPTE drop-frame timecode emitted by the API) and placed through a purpose-built frame-stepping player with a scrubber marker track and in/out range selection.
| HTTP REST and GraphQL APIs (for assets/folders generally) | ✅ Done | ~44 REST controllers plus a full GraphQL schema (queries, 33+ mutations) covering assets, folders, collections, and search.
| Marketing Cloud integration | ➖ N/A | Adobe Experience/Marketing Cloud–specific. No Salesforce Marketing Cloud or Adobe Experience Cloud connector exists, and none is currently planned — Capri DAM's integration surface is its own REST/GraphQL API plus the 13 ingestion connectors below.
| Customize and extend the asset management UI | 🚧 Partial | Custom **metadata fields** are fully supported (Metadata Schemas admin tool). A general UI plugin/widget-extension framework (custom dashboard widgets, custom Properties tabs) does not exist yet (tracked above); its design is decided in *ADR 7*.
| Query Builder API to extend search | ✅ Done | A validated nested boolean query AST — groups of `{op: and/or/not, children}` over leaves of `{field, operator, value}` — compiled to SQL in exactly one place, plus a recursive React builder for it. The flat search params were implicitly AND-ed, which is right for a facet bar and cannot express `(shot_on_location OR studio) AND NOT expired`; what was missing is *structure*, not vocabulary, so no further params would ever have got there. `Search::FieldRegistry` is the allow-list: `assets.properties` is a jsonb blob holding curated metadata alongside `checksum_sha256`, `storage_path` and `thumbnail_data`, and reflection cannot tell those apart, so a field is unreachable until it is listed. The registry also records the types JSON does not have — `(properties->>'file_size')::bigint` is only safe because we decided that key holds an integer. `GET /api/v1/search/fields` serves that same registry to the builder, so the pick-list a user sees and the allow-list the compiler enforces cannot drift; a hardcoded client list would fail as a broken query rather than a stale constant. Schema-defined metadata fields resolve at request time from `MetadataSchema` tabs via `map_to_property` only, with static definitions winning a name collision so an administrator cannot redefine `title`. Four limits — depth 8, 100 nodes, 50 list values, 500-character values — are checked during the walk before any SQL is produced, because caller-supplied structure recurses and a few kilobytes of nested JSON would otherwise become thousands of predicates. `not` takes exactly one child rather than guessing between "not all of these" and "none of these", which differ on every partially-matching row; an empty group compiles to no constraint rather than the logically-pure `FALSE`, since in a builder it means unfinished, not false. `not_eq` compiles to `IS DISTINCT FROM`: an asset with no `content_type` genuinely is not equal to `image/jpeg`, and `<>` would silently drop it. Property casts sit inside a regex-guarded `CASE` — one row holding `"unknown"` in `file_size` would abort the whole query, and an `AND` guard would not help because Postgres does not promise left-to-right evaluation — with the same treatment for a `tags` key that is not an array. `LIKE` wildcards typed into a *contains* box are escaped to literals, and date `eq` means "on that day" rather than an exact instant that would never be true. The AST is AND-ed onto the flat params rather than replacing them: the params are a facet bar, the AST is arbitrary field logic, and layering them is what "these filters, plus this query" means — so every existing param keeps its tested code path and the change is purely additive. `query` had to become a reserved param name, or the AST's JSON string would have been swept into `properties->>'query' IN (...)`. The builder round-trips — an AST loaded from the server renders back into the tree it was built from, and rides in the URL so a shared link reopens the conditions, not just the results — which is what makes it worth having over a text query language. Conditions with no field yet are omitted rather than sent, since a freshly added row would otherwise fail the live count on every click. That count (`POST /api/v1/search/count`) is debounced, abandons superseded in-flight requests so a slow early response cannot pin the wrong number on screen, and is the one search response deliberately left uncached. GraphQL `searchAssets` gained the same AST as a `filter` argument; `metadataFilters` is deprecated rather than removed. See `docs/developer-guide/src/34_query-builder.adoc`.
| Create static tags | ✅ Done | Manual tag editor (`AssetTagsEditor`) with autocomplete, kept separate from AI-suggested tags; workflow nodes can also add/remove tags automatically.

Threads live on the *asset* while each comment records the *version* it was written against, so feedback is not orphaned by a re-upload.

| Fixity checking & digital preservation | ✅ Done | Stored bytes are periodically re-hashed and compared against the SHA-256 recorded at ingest, because storage does not announce that it has lost something — bit rot, a truncated upload and a well-meaning bucket cleanup all look identical until the day the file is needed, by which point the corruption is usually in every retained backup generation. `FixityAuditWorker` verifies a budgeted, staleness-ordered sample nightly rather than sweeping the estate, since a full sweep means downloading everything and is an egress bill that gets the whole audit switched off after the first invoice. Four verdicts are kept distinct — `passed`, `failed` (bytes changed), `missing` (storage/path problem) and `unreadable` (inconclusive) — so a network fault can never raise a corruption alarm, and versions ingested without a checksum are reported as an *unverifiable* coverage gap rather than as failures. `Preservation::FormatRegistry` answers the question that outlives fixity: a perfectly intact SWF or FLV passes every integrity check ever run against it and is still unreadable. Reported via the `/api/v1/preservation` endpoints (`fixity`, `verify`, `formats`). See `docs/developer-guide/src/35_fixity-and-preservation.adoc`.
| Entity graph (people, places, products, campaigns) | ✅ Done | The library now records *things*, not just strings. A tag reading `jane-doe` cannot distinguish two people who share a name, cannot say whether Jane is in the photograph or took it, and does not know that `berlin`, `berlin-de` and `Berlin, DE` are one city — and each of those is a question a DAM is eventually asked. `Entity` gives each subject a typed record (person, place, product, brand, campaign, event) with aliases for the alternate spellings, and `AssetEntity` states *how* an asset relates to it through a closed five-relationship vocabulary (`depicts`, `shot_by`, `belongs_to`, `located_at`, `mentions`) constrained per entity type — `shot_by` accepts only a person, which is what makes "who took this?" answerable at all. The vocabulary is deliberately closed rather than an open triple store: an unbounded predicate set cannot be indexed, offered as a UI control, or reasoned about by a consent or rights policy. `Entities::Resolver` proposes links from existing tags but never asserts them — tags are read and never rewritten so the pass stays re-runnable, a tag matching two entities is reported as ambiguous rather than guessed, and `shot_by` is never inferred from a tag. Every machine-derived link stays unconfirmed until a person agrees, and policy consumers read `asserted` rather than `source`. Duplicates are merged, never deleted: the loser keeps a `canonical_id` pointing at the survivor and donates its name as an alias, so existing links, saved searches and integration slugs all keep resolving. Six search fields (`entity:`, `depicts:`, `shot_by:`, `belongs_to:`, `located_at:`, `mentions:`) compile to a correlated `EXISTS` rather than a join, so filtering never multiplies the caller's rows. Exposed over REST, GraphQL (`entities`, `entity`, `Asset.entityLinks`) and the query builder. See `docs/developer-guide/src/36_entity-graph.adoc`.
| Rights management / licensing | ✅ Done | Assets carry typed, constrained `usage_terms` and `license_expires_at` columns with a controlled vocabulary and an ISO-8601-only expiry parser; `Rights::DownloadPolicy` enforces them on guest review links, watermarked export, bulk ZIP download and download-URL issuance; and `AssetRightsPanel` on the asset viewer manages them. Enforcement is fail-closed — anything the backfill could not confidently classify defaults to `internal_only` and is therefore not shareable externally until someone classifies it.
