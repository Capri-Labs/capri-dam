[cols="1,2,3", options="header"]
|===
| Status | Item | Description

| ✅ Done | MUI v9 migration | All components use `slotProps`; deprecated prop aliases removed.
| ✅ Done | Keycloak SSO | OmniAuth-based enterprise SSO.
| ✅ Done | Duplicate Manager | Checksum-based detection with resolution UI.
| ✅ Done | Recycle Bin | Soft-delete with configurable retention and workflow guard.
| ✅ Done | Workflow Designer | `@xyflow/react` DAG canvas with approval and automation steps.
| ✅ Done | AI Copilot | Natural-language asset discovery via chat.
| ✅ Done | pgvector semantic search | Cosine similarity + semantic cluster map.
| ✅ Done | Audit log refactor | Immutable, DB-trigger-protected audit trail; structured operational logging.
| ✅ Done | Rebranding | "Capri DAM" logo/icon refresh.
| ✅ Done | AVIF delivery | Delivery requests are answered in AVIF (preferred) or WebP when three parties agree, each of which can veto. The *administrator* must have enabled the format in `image_optimizer_formats` on the active CDN configuration — the allow-list that already existed now governs what the application itself produces as well as what an edge CDN may serve, so one switch means one behaviour with or without a CDN in front, and with no active configuration nothing is transcoded at all. The *client* must name `image/avif` or `image/webp` explicitly in `Accept`: a wildcard is not evidence, because every browser sends one regardless of what it can decode, and a browser handed a format it cannot decode shows a broken image rather than a larger one — Safari and older Chrome/Firefox advertise WebP but not AVIF, which is why the negotiator falls back rather than assuming. The *encoder* must come out smaller: AVIF's fixed overhead can exceed what it saves on small images, and serving a larger file would be a pessimisation disguised as a modernisation, so a derivative that fails to pay for itself is discarded and the original served. Only JPEG and PNG are re-encoded — SVG because re-encoding a vector destroys the reason it is one, GIF because it may be animated and a single-frame AVIF would silently truncate it. Derivatives are content-addressed files keyed on the source's size and mtime plus the encode settings, not `renditions` rows: a delivery derivative is disposable and giving it a database row would mean inventing a storage backend for it and keeping row and file in step on every re-upload, whereas the digest gets invalidation for free. `Vary: Accept` is set on every response including 304s and untranscoded originals, since a shared cache keyed only on the URL would hand an AVIF to a client that cannot decode it; the ETag is computed over the bytes actually sent, since a shared one would let a client holding the JPEG revalidate into a 304 and never receive the AVIF. Every failure path serves the original rather than raising — this runs inline on an image request, so a missing codec must degrade, not 500. Request-time *resizing and cropping* remain edge-only; the in-application pipeline negotiates format.
| ✅ Done | Kamal 2 deployment | Production deployment via Kamal 2 (`kamal` 2.12.0). `config/deploy.yml` defines web + Sidekiq worker roles, `kamal-proxy` with automatic Let's Encrypt TLS and a `/up` health check, GHCR image pull matching `.github/workflows/docker.yml`, and PostgreSQL (pgvector) + Redis accessories with persistent volumes. `.kamal/hooks/pre-deploy` gates on a clean tree and green CI; `.kamal/hooks/post-deploy` runs an HTTPS smoke test; `.kamal/secrets` references env vars only. The 10-chapter playbook in `docs/deployment-guide-kamal/` (prerequisites → configuration → secrets → accessories → first deploy → routine deploys/rollback → SSL → monitoring → backup/DR) is published as HTML + PDF by `.github/workflows/main.yml`.
| 📋 Planned | Multi-site isolation | Tenant-scoped storage and RBAC for agency use cases.
| 📋 Planned | DAM-to-DAM federation | Cross-instance asset sharing via signed GraphQL federation.
| 📋 Planned | AI auto-tagging | Automatic tag suggestions from a computer-vision model at upload time.
| ✅ Done | Bulk copy (folders & assets) | "Copy to…" action mirroring the existing "Move to…" action — select any mix of folders/assets and copy them into a new destination in one request (`POST /api/v1/copy_operations`). Recursively duplicates folders, shares the source's ActiveStorage blob instead of re-uploading bytes, and auto-resolves name collisions.
| ✅ Done | Bulk/folder ZIP download | "Download" action on a folder or any multi-asset selection streams a ZIP built asynchronously by `AssetDownloadWorker`, with a live progress bar, queue-awareness (a second download while one is running is queued, not run concurrently), and the finished ZIP link delivered to the user's Inbox and notification bell.
| 📋 Planned | Manual static renditions | User-facing "Add/Delete rendition" action on an asset's Properties page (`renditions` table and model already exist; today renditions are worker-generated only — video MP4/OGG/AV1 — with no CRUD UI or endpoint).
| ✅ Done | Direct Publish REST action | `POST/POST /api/v1/assets/:id/publish`\|`/unpublish` — publishing an asset no longer requires building a workflow first. "Manage Publish" is a dedicated menu next to (not inside) *Tools* in the Explorer, offering immediate Publish/Unpublish plus "…Later" scheduling (`ScheduledPublishAction` + `PublishSchedulerWorker`, polled every 5 minutes) for a future date/time. Asset-only — never shown for a selection containing folders.
| ✅ Done | Contextual metadata rules (Choices / Requirement / Visibility) | Metadata Schema fields can depend on another `select` field's value, configured entirely via the Schema Editor UI (no code changes): **Choices** narrows a dependent `select`'s options (`field.rules.cascade`); **Requirement** dynamically marks any field type required (`field.rules.requirement`); **Visibility** shows/hides any field type (`field.rules.visibility`). Resolved client-side by `AssetMetadataPanel#resolveFieldRules`, with save-time validation across all tabs.
| ✅ Done | Custom "funny 404" error page | A shared `ApplicationController#render_not_found` (triggered by `ActiveRecord::RecordNotFound` and by a `config/routes.rb` catch-all for unmatched routes) replaces raw Rails diagnostics pages with an illustrated, on-brand 404 screen for browser navigation, and a small structured `{ error: ... }` JSON body for API/fetch clients — e.g. a stale `/api/v1/asset_downloads/:id/download` inbox link no longer surfaces a stack trace.
| ✅ Done | Image coordinate annotations | Draw a pin, rectangle, ellipse, arrow, line or freehand markup directly on an image preview and attach it to a comment. Geometry is stored *normalised* (0..1, upper-left origin, DB `CHECK`-constrained) plus an `svg_path` in a `viewBox="0 0 1 1"` space, following the W3C Web Annotation Data Model's FragmentSelector/SvgSelector split — so one annotation lands correctly on a thumbnail, a full-size preview, a CDN transform and a zoomed viewport alike, and never breaks when a rendition is regenerated. `annotation_targets` also records the source dimensions/rotation at annotation time so the geometry can later be re-projected onto a differently sized version. `AnnotationOverlay.jsx` renders the shapes as individually selectable SVG nodes stacked on the preview; clicking a marker jumps to its thread and vice versa.
| ✅ Done | General asset commenting | A standalone, threaded review conversation on any asset (`comment_threads` / `comments`), open to anyone with `:read` on the folder — deliberately *not* `:modify`, because reviewing is not editing. Replaces the previous situation where the only "comment" in the product was the approve/reject note on a workflow task. **Threads belong to the asset; each comment records the `AssetVersion` it was written against** — so a thread survives re-uploads instead of being orphaned by them (the limitation every comparable product documents). Lifecycle is `open → addressed → verified → resolved`, with `verified` reserved for a reviewer confirming a fix actually landed. `@mentions` reuse the existing `MentionDetectionService`/Inbox/notification-bell/email pipeline; edits stamp `edited_at` and deletes are soft, so the trail cannot be silently rewritten. Editing or deleting a comment is author-only. REST at `/api/v1/assets/:id/comments`, `/api/v1/comment_threads/:id` and `/api/v1/comments/:id`; UI in the Explorer asset viewer's *Comments* tab.
| ✅ Done | Video timestamp & range annotations | Comment on a single frame or on an in/out *range*, with a custom frame-accurate transport (`VideoAnnotationPlayer`): frame stepping, SMPTE timecode readout, a marker track on the scrubber, loop playback over the selected range, and the standard NLE keyboard bindings. Markup drawn on the video is stamped with the frame it was drawn over and only appears while the play head is inside that range, so an arrow pointing at a car does not linger after the car has driven off. A spatially-empty `time` shape lets a reviewer comment on a moment without drawing anything. Frame rate now comes from ffprobe (`avg_frame_rate`, falling back to `r_frame_rate`), keeping the exact rational so 29.97 can be told apart from a true 30 and drop-frame applied correctly.
| ✅ Done | Cross-version comment lineage | Auto-answer "was this feedback actually addressed?" by re-projecting a thread's stored (normalised) bounding box onto a newer version and running the canvas pixel-diff that `AssetVersionsTab.jsx` already implements *inside that region* — surfacing an automatic "changed in v3" / "unchanged since v2" marker on each thread, and offering side-by-side before/after crops of just the annotated region. No reviewed competitor carries comments forward across versions at all, so this is a genuine differentiator rather than parity work.
| ✅ Done | Guest reviewers & external review links | Let a client review and comment on an asset or a whole collection without a Capri account, via a revocable, time-boxed link (`/s/reviews/:token`). Capri already had *read-only* collection share links built on Rails `signed_id`, but a self-describing signed token cannot be revoked, carries no identity and cannot be scoped or metered — all three of which a link granting **write** access needs — so review links are DB-backed (`review_links`, `review_guests`) while share links are left as they are. Only a SHA-256 digest of the token is stored, so the raw token is shown exactly once at creation and a database dump yields no working review URLs; an optional passphrase (bcrypt, human-chosen, so a slow digest is the right one there) adds a second factor shared out of band. Expiry is mandatory and hard-capped at 180 days. A collection link resolves through *live* membership, so removing an asset from the collection withdraws it from every outstanding link at once. Guests are identified for **attribution, not authentication** — a `ReviewGuest` is not a `User`, so it has no credentials to compromise and no permission surface to widen, and a self-asserted email is never matched against an existing account. The guest surface shares serialisation with the internal API but *no authorisation path*: there is no `if guest then skip the permission check` branch anywhere, and the guest serialiser is an allow-list, so internal staff emails and user ids cannot leak. `comment_threads.visibility` (`internal` / `guest`) filters at the query, not in the view. Previews and downloads are proxied through the app rather than handed out as signed storage URLs, so revocation actually revokes. Guests can open threads, annotate and reply; they cannot resolve, verify, reopen, edit or delete. Managed at `/api/v1/review_links`, which requires `:modify` on the target — sharing outside the organisation is a stronger act than discussing internally.
| ✅ Done | Annotation interoperability & export | Emits and ingests W3C Web Annotation JSON-LD, so a proofing vendor, archive or approvals system is a file copy rather than a bespoke integration. Geometry travels as percentage media fragments (never pixels, so an export is not tied to whichever rendition was on screen), with an `SvgSelector` for non-rectangular shapes and a `t=` temporal fragment for video. What the standard cannot carry — shape, stroke style, exact frame rate, drop-frame, thread grouping — rides *alongside* it under a namespaced `capri:` prefix, so third parties see valid W3C while Capri round-trips losslessly. Import treats the file as untrusted input: attribution is never honoured (the uploader is always the author, the file's claim kept as provenance), visibility is forced to `internal`, and a claimed `resolved` is gated on `:modify` so an upload cannot silently close outstanding feedback. Also renders an annotated PDF contact sheet for offline sign-off — markers drawn as vectors over the preview so they stay crisp in print, degrading to a text-only sheet rather than failing if the preview is unreadable — and fires HMAC-signed review webhooks (`comment.created`, `comment.resolved`, `thread.created`, `thread.resolved`, `thread.reopened`) from a proper subscription registry, scoped per asset or folder, distinct from the workflow engine's per-step webhook action.
| ✅ Done | AI review assistant | A vision model runs over an asset and posts what it finds (brand-guideline breaches, unreadable contrast, logo outside the safe area, off-brand colour) as *real* annotated comments — the same threads, normalised geometry and version binding as a human remark — which a person then accepts or dismisses. Findings are stored as ordinary `CommentThread`s rather than in a parallel suggestions table, so region-diff across versions, W3C export and the PDF contact sheet all applied to machine output on day one; a separate table would have needed every one of them reimplemented and the two would have drifted. What separates a suggestion from feedback is `comment_threads.suggestion_state`, NULL for every human thread and `pending` for a machine one: until somebody accepts it a finding is excluded from the thread list, from exports and from the guest surface, and is additionally created `internal` so the guest query excludes it twice over — an unreviewed machine guess reaching a client is the worst outcome this feature has. Accepting records *who decided* but never rewrites the comment's author: `agent_type` stays `software` for ever, because laundering machine output into a person's name would destroy exactly the audit trail that column exists to keep. Dismissed findings are kept, not deleted — a false positive is the only evidence available for tuning the model. Inference stays in the AI gateway (Rails publishes `ai_review.dispatch` over Redis and the gateway calls back with the shared secret), the dispatch carries a callback URL rather than storage credentials so revoking a run revokes its access, and the callback payload is treated as untrusted: coordinates clamped into the unit square, bodies capped, low-confidence findings dropped, runs capped at 50, one malformed finding skipped rather than fatal. Requesting a run needs `:modify`, not the `:read` ordinary commenting needs, since it discloses the asset to an external service and spends budget; `profile` is an allow-list, not a free-text prompt. Triage lives in the Comments tab of the asset viewer, above the human threads, because a suggestion is a comment thread awaiting admission — accepting one makes it appear in the list directly below. Suggestion markers are drawn on the shared annotation overlay in the assistant's purple, stamped server-side so the UI and the W3C export cannot disagree about which marks are machine-made. There is deliberately no "accept all": the assistant's value is that a human looked at each claim, and a bulk button would quietly turn it into an unreviewed bot posting into the client's review. The queue polls only while a run is in flight — findings arrive by gateway callback, nothing pushes to the browser — and stops the moment the run is terminal.
| 📋 Planned | UI extension/plugin framework | A documented hook/widget API so third parties can add custom panels, dashboard widgets, or Properties-page tabs without forking the React source (custom *metadata fields* are already fully supported via Metadata Schemas — this item is about extending the *UI itself*, e.g. new widget types beyond the single built-in `BarChartWidget`).
| 📋 Planned | Distribution portal for external stakeholders | Expand today's signed, time-expiring Collection share links into a full-fledged branded portal with per-asset (not just per-collection) permissions and download tracking for external reviewers/partners.
| 📋 Planned | Rights & licensing enforcement | Turn today's rights *metadata* (`usage_terms`, `license_expires_at` on Asset; compliance-violation checks on Collections) into enforced behaviour — e.g. blocking download/export of an expired-license or internal-only asset, plus a licensing-terms management UI.
|===

=== Capability parity checklist (vs. a typical enterprise DAM suite)

The table below was produced by directly auditing this codebase (models,
controllers, GraphQL schema, and React components — not assumptions) against
a checklist of capabilities commonly expected of an enterprise DAM/Assets
product. It is meant to answer "is X implemented, partial, or not built yet"
for planning purposes. Genuine gaps are already reflected as
📋 Planned rows in the <<module-roadmap,product roadmap>> above.

[cols="3,1,5", options="header"]
|===
| Capability | Status | Notes / evidence

| Create folders to organize assets | ✅ Done | Hierarchical `Folder` model (self-referential nesting), full CRUD, breadcrumbs, soft-delete.
| Upload assets | ✅ Done | Single + bulk drag-drop upload, duplicate detection, schema assignment at upload time.
| Publish assets | ✅ Done | `Asset#status` still includes the older workflow-driven `ready`/`approved` states, but publishing is now also a direct, one-click action independent of any workflow: `POST/POST /api/v1/assets/:id/publish`\|`/unpublish` (immediate or scheduled for a future date/time via `ScheduledPublishAction`/`PublishSchedulerWorker`), surfaced through the "Manage Publish" menu next to *Tools*.
| Edit, move, and copy assets | ✅ Done | Edit, move, and copy are all full REST actions (`Api::V1::Assets#update`, `Api::V1::MoveOperations#create`, `Api::V1::CopyOperations#create`). Copy recursively duplicates folders (subfolders + assets), shares the underlying ActiveStorage blob rather than re-uploading file bytes, and auto-resolves destination name collisions.
| Browse, filter, and search assets, including similarity search | ✅ Done | Full-text + faceted REST search, pgvector cosine-similarity semantic/visual search, agentic AI Copilot search mode.
| Add/edit Basic-tab metadata field values (except Smart Tags) | ✅ Done | Schema-driven `AssetMetadataPanel` with per-field `read_only` support; AI-generated tags are shown read-only and separated from manually-editable static tags.
| Add and delete static renditions | ❌ Not built | `Rendition` model/table exist but are worker-generated only (video MP4/OGG/AV1); no user-facing add/delete UI or endpoint yet (tracked above).
| Download folders, assets, and asset renditions | ✅ Done | Individual asset + individual rendition download; bulk folder/asset ZIP export via `AssetDownloadWorker` with progress polling, queue-awareness, and inbox/notification delivery of the finished link (`Api::V1::AssetDownloadsController`).
| Create asset versions | ✅ Done | Full immutable version history per asset with restore-to-prior-version support.
| Create and perform review tasks on assets | ✅ Done | Workflow approval nodes with configurable assignees/any-all logic, SLA deadlines, and a Workflow Dashboard of pending/active/completed tasks.
| Annotate assets (coordinate/timestamp pins) | ✅ Done | Pin, rectangle, ellipse, arrow, line and freehand markup on image *and video* previews, attached to a comment. Geometry is stored normalised (0..1) with an `svg_path` in a `viewBox="0 0 1 1"` space, per the W3C Web Annotation Data Model, so it survives responsive layout, renditions and CDN transforms. Video positions are stored frame-accurately (`start_frame`/`end_frame`/`fps`/`drop_frame`, with SMPTE drop-frame timecode emitted by the API) and placed through a purpose-built frame-stepping player with a scrubber marker track and in/out range selection.
| HTTP REST and GraphQL APIs (for assets/folders generally) | ✅ Done | ~44 REST controllers plus a full GraphQL schema (queries, 33+ mutations) covering assets, folders, collections, and search.
| Marketing Cloud integration | ➖ N/A | Adobe Experience/Marketing Cloud–specific. No Salesforce Marketing Cloud or Adobe Experience Cloud connector exists, and none is currently planned — Capri DAM's integration surface is its own REST/GraphQL API plus the 13 ingestion connectors below.
| Customize and extend the asset management UI | 🚧 Partial | Custom **metadata fields** are fully supported (Metadata Schemas admin tool). A general UI plugin/widget-extension framework (custom dashboard widgets, custom Properties tabs) does not exist yet (tracked above).
| Query Builder API to extend search | 🚧 Partial | REST search accepts arbitrary metadata/property query params, and GraphQL `searchAssets` accepts a `metadataFilters` map — but there's no graphical query-builder UI and no complex nested boolean-query support.
| Create static tags | ✅ Done | Manual tag editor (`AssetTagsEditor`) with autocomplete, kept separate from AI-suggested tags; workflow nodes can also add/remove tags automatically.
| Author projects and tasks | ✅ Done | `Collection` model serves as the project/campaign workspace (manual or rule-based "smart" membership, group ACLs, expiry); Workflow Tasks provide the task layer.
| Activity stream (timeline) | ✅ Done | Immutable, DB-trigger-protected `AuditLog` plus per-asset usage-event tracking (views/downloads/shares), surfaced in the asset's Audit tab.
| Comments and annotations | ✅ Done | Threaded, general-purpose review conversations on any asset, independent of workflows, with an `open → addressed → verified → resolved` lifecycle, `@mention` notifications through the existing Inbox/bell/email pipeline, author-only edits (stamped `edited_at`), soft deletes, and spatial annotations anchored to the media. Threads live on the *asset* while each comment records the *version* it was written against, so feedback is not orphaned by a re-upload.
| Doorkeeper OAuth2 / API auth for integrations | ✅ Done | Full OAuth2 (Doorkeeper) plus GraphQL-managed Personal Access Tokens for third-party API clients.
| Third-party ingestion/migration connectors | ✅ Done | 13 source connectors (AEM, Aprimo, Brandfolder, Bynder, Canto, Cloudinary, Extensis, FTP, Media Valet, Nuxeo, S3, SharePoint, Widen) with encrypted credentials.
| Distribution portal for external stakeholders ("Content Hub") | 🚧 Partial | Collections can be shared externally via signed, time-expiring links today; a full branded, per-asset-permission portal is not built yet (tracked above).
| Dynamic Media (image/video transformation & delivery) | ✅ Done | Real-time edge CDN delivery, smart subject-aware cropping, multi-codec video encoding (H.264/AV1/VP9), HLS/DASH streaming, signed URLs, per-folder delivery profiles. AVIF/WebP are now negotiated at request time by the application itself, gated on the administrator's allow-list, the client's `Accept` header and the encode actually being smaller; request-time resizing and cropping remain edge-only.
| Rights management / licensing | 🚧 Partial | Assets store usage-terms and license-expiry metadata, and Collections flag compliance violations — but nothing is *enforced* yet (e.g. an expired-license asset can still be downloaded), and there's no licensing-terms management UI (tracked above).

=== Consolidated test-coverage roadmap

This guide's screenshots and feature descriptions are accurate as of today, but
**E2E test coverage across the product is uneven** — some modules (Recycle Bin,
Access Control) are exercised extremely thoroughly, while others (Delivery & CDN,
System Operations sub-tabs, several AI features) have little to none. The table
below consolidates every `[.status-pending]` item called out per-module into a
single backlog, to help prioritise future E2E test-writing.

[cols="2,4", options="header"]
|===
| Module | Pending E2E scenarios

| Dashboard | ✅ Widget-level interaction/drill-down now covered (see <<module-dashboard>>) — KPI-card value accuracy after live data changes, and Asset Growth chart / Workflow-summary count updates remain pending.
| Asset Management | ✅ Now covered: version history diff view (real end-to-end pixel-diff test, surfacing and fixing two genuine bugs — a `crossOrigin`/cookie-stripping bug and a local-storage version-URL routing bug), bulk metadata CSV import/export (real upload/processing/download round-trip). See <<module-asset-management>>.
| Search & Discovery | ✅ Now covered: semantic search relevance/ranking (real pgvector query against seeded embeddings), semantic cluster map rendering + node hover interaction. See <<module-search>>.
| Recycle Bin | ✅ Now covered: restoring an item back to the active library; permanently purging via Empty Bin end-to-end; workflow-protected purge guard (skip behaviour); retention-policy save (persists across reload).
| Workflow Automation | Parallel/Sequential Review and Slack/In-App Alert nodes; full workflow execution (trigger → task → resolution); Workflow Dashboard screen; editing a published blueprint.
| Access Control & Security | OAuth2 (Doorkeeper) token issuance; server-side enforcement of the 7-column ACL; full Keycloak OIDC round-trip.
| AI Intelligence Suite | AI Copilot chat interaction; Agent Automations; Batch Processing; Prompt Playground; creating a model endpoint/style preset; C2PA record signing.
| Email / Communication Engine | Real email send/receive round-trip; event-mapping creation; AI Suggestions generation; Outbox filtering.
| Ingestion & Migration | Completing the migration wizard against a real connector; Legacy Connectors screen; batch execution monitoring; per-source-platform behaviour.
| System Operations & Admin | ✅ Now covered: Observability tab (vitals + restart flow), Operational Logging save flow (incl. TRACE level), AI Gateway controls (simulated UI), Feature Flags placeholder, Reports screen (Analytics Dashboard, Download Center, Report Types, Create Export drawer), Storage & Edge CDN provider switch (Fastly/Cloudflare/Akamai credential fields + persistence).
| Localization / i18n | ✅ Now covered: E2E switching/persistence for all 10 locales (German plus the 7 previously-untested locales — Spanish, French, Japanese, Korean, Dutch, Portuguese, Chinese); Arabic sets `<html dir="rtl">` immediately and after reload, with a real-translation sanity check; both the Profile page and Admin → Edit User drawer language dropdowns now correctly offer Arabic (a prior bug had it missing from both). **Still pending**: full MUI-level RTL mirroring (current implementation is `dir`-attribute only, not a themed `direction: 'rtl'` + stylis RTL plugin); native-speaker quality review of `ar.json` (most values are still placeholder English copies, though key-parity is enforced).
